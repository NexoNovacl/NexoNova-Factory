## Arquitectura y contratos

`factory/generation.py` valida y escribe bytes; no instala ni ejecuta código web. `scripts/generate_corporate_site.py` expone stage/review/materialize/discard. `factory/web_tools.py` y su CLI realizan validación preparatoria explícita en una copia descartable. `factory/product_integrity.py` verifica el producto contra el manifiesto de generación y detecta imports/recursos locales estáticos rotos.

Entradas explícitas: WorkOrder de producto v2, especificación corporate-site v0.1.0, manifiesto de fuentes v1, configuración pública visual v1, selección de generación v1 y manifiesto del template v1/version 0.1.0. El WorkOrder enlaza los cinco hashes; `config/generation.json`, bajo control del operador, autoriza su hash exacto y raíces relativas. Un contrato que se reautorice a sí mismo no satisface esta política. No se interpreta código ni comandos aportados por el cliente.

Los contratos P2 y de preparación P3.2 v1 permanecen intactos. El gate v1 `--require-ready` sigue rechazando material pendiente; no se relajó. La nueva orden v2 autoriza exclusivamente el piloto interno con selección explícita: cero assets del prototipo, las 99 rutas originales y los cinco recursos ausentes omitidos, referencia visual sin copia, fallback de Inter sin archivo local y contenido provisional. Esto materializa las decisiones aprobadas, sin declarar aprobados los materiales REVIEW. Todos los pendientes deben estar resueltos para este alcance en la selección; campos incompatibles o incoherentes bloquean.

El template congelado contiene 30 archivos. La generación copia esa base, inyecta el JSON público, adapta solamente el nombre raíz de package.json/package-lock.json y crea `.nexonova/project.json`. No contiene ramas por cliente. Las restricciones actuales exigen la composición de secciones implementada: no se simula soporte de variantes todavía no construidas.

## Determinismo, metadata y seguridad

El baseline incluye los hashes de las fuentes anteriores a las herramientas. `.nexonova/project.json` contiene versiones, projectId, tipo, hashes públicos y baseline portable, sin WorkOrder, autorizaciones, rutas privadas ni briefs. El baseline no contiene su propio hash recursivo; el manifiesto exterior sí incluye el archivo de metadata. El sitio no importa esta metadata.

No hay timestamps ni UUID dentro del producto. Los nombres aleatorios de staging/contenedores, resultados operativos, duraciones y rutas locales pertenecen a registros externos y no al hash estable. La reproducibilidad demostrada corresponde al código generado, no a node_modules o builds binariamente idénticos.

Next.js regenera `next-env.d.ts` durante el build. El validador informa este cambio por separado y solo acepta la forma exacta conocida de Next 15; no la presenta como idéntica al baseline. `.next`, node_modules, informes de pruebas y tsbuildinfo son derivados, no fuentes generadas. Para revalidar en limpio, el adaptador restaura el bootstrap aprobado únicamente en su copia descartable; no reescribe el producto original.

Se rechazan traversal, rutas ambiguas/absolutas aportadas como destino, salida fuera de raíz, solapamiento con fuentes, symlinks/hardlinks de archivos fuente, colisiones de mayúsculas/minúsculas y destino existente, incluso vacío. Hay límites de cantidad/tamaño de entrada, escrituras exclusivas, lock de staging y revisión de hashes antes de publicar. Materialize exige el hash explícito del diff y un recibo exitoso de las seis acciones web para ese contenido. Linux `renameat2(RENAME_NOREPLACE)` evita sobrescribir durante la publicación; no existe --force.

El descarte solo opera sobre staging registrado e íntegro. Una generación incompleta o alterada exige inspección manual; no hay borrado amplio. Los registros de aprobación son evidencia local bajo host confiable, no firmas resistentes a un operador malicioso.

El adaptador permite solo version/probe/install/typecheck/test-content/build. Instalación: npm ci --ignore-scripts --no-audit --no-fund, lock aprobado y URLs registry.npmjs.org. Solo esa preparación usa red bridge; las demás acciones usan network=none. El control de URLs no equivale a un firewall de salida. Host y daemon siguen siendo confiables según P2.

Los contenedores usan raíz readonly, usuario 1000:1000, capabilities vacías, no-new-privileges, CPU 2, memoria 2 GiB, PIDs 256, tamaño de archivo limitado y tmpfs acotado. Solo se monta la copia de trabajo; sin puertos, home del operador, socket montado ni secretos. El probe observó únicamente loopback, escritura raíz denegada, sentinel privado ausente y los límites cgroup esperados. Cada acción registra nombre real, comando, código y limpieza. Además verifica que no alteró fuentes autorizadas. Se limita salida y tiempo y se eliminan contenedores/copia temporal.

## Errores, límites y revisión pendiente

Primer intento de instalación Docker: npm rechazó cargar /dev/null a la vez como configuración global y de usuario. Se corrigió la ubicación global a un archivo inexistente del tmpfs; se conserva [el fallo original](P3_5_WEB_INITIAL.json). No se redujeron controles. Se detectó y trató explícitamente la regeneración de next-env.d.ts; no se relajó la comparación determinista.

Persisten: publicación soportada en Linux y mismo filesystem; sin garantía ante corte eléctrico/SIGKILL ni recuperación automática de publicación interrumpida; inspección manual de recursos/metadata tras crash. No se implementa actualización de productos existentes. La redacción es heurística secundaria; la independencia se verifica en fuentes y comportamiento observado, no acredita eliminación absoluta de secretos en cualquier binario/vendor. No se ejecutó auditoría de vulnerabilidades ni se certifica la cadena de suministro; imagen/lock requieren mantenimiento operativo. El navegador todavía no está integrado en el adaptador Docker acotado.

Assets REVIEW, cinco recursos ausentes, Inter local y aprobación comercial definitiva siguen fuera; no hay referencias runtime a ellos. Procedencia del legado/Git y aprobación de publicación siguen pendientes. La segunda configuración sintética formal y ausencia de contaminación entre productos corresponden a P3.6 y no se declaran demostradas aquí.

Revisión humana solicitada: generador/política de autorización, diff y producto materializado; aceptar límites experimentales y decidir si autorizar P3.6. Sin ejecución automática de fases posteriores.
