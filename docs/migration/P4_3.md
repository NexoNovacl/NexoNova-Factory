## Migración, privilegios y persistencia demostrados

1. Dos redes internas, dos DBs/volúmenes propios y contraseñas distintas por rol/run. DB A vacía: cero tablas del schema app.
2. Migrador aplica el historial fijo de TechnicalSmoke. Segunda aplicación conserva exactamente migration_name/checksum/finished_at y una sola entrada completada.
3. Runtime tiene USAGE/CRUD explícitos, no ownership/DDL. CREATE TABLE con su conexión real es rechazado por PostgreSQL con **SQLSTATE42501**. El intento de usar directamente Prisma Migrate con runtime también falla, sin depender solo del guard de nombres.
4. Prisma/runtime escribe marcador exclusivamente sintético y lo lee después de dos arranques de Next. Luego se detiene PostgreSQL ordenadamente, se inicia Compose con **el mismo volumen de ese run**, se lee desde el propio servicio app, se reinicia app y se vuelve a leer. No hay API pública de la fixture. Esto demuestra persistencia básica, no backup/restore.
5. Desde la red B se intenta acceder a la IP de DB A usando credenciales A válidas: falla. B no monta volumen A ni socket Docker. Su propio historial aplicado tiene cero filas del marcador A; runtime B no encuentra el dato. No se afirma resistencia frente a un operador/daemon host malicioso.
6. La migración inválida deliberada existe únicamente en la copia temporal de B: Prisma falla y el historial conserva entrada incompleta con SQLSTATE42601. Nunca se modifica el historial aceptado del core ni se ejecuta reset/db push.

## Compose y controles

App/DB reales con red interna y **ningún puerto publicado**; socket Docker nunca montado dentro de contenedores. Inspección confirma root readonly, capabilities vacías, no-new-privileges y límites CPU/memoria/PIDs. El intento real de escribir `/app/forbidden` falla. Estos límites se inspeccionan; no se reclama haber provocado OOM/saturación de CPU/PIDs.

Herramientas Node offline montan solo su copia temporal de trabajo y usan env explícito. Compose app monta el proyecto como readonly y recibe solo DATABASE_URL; migrador usa su URL separada; DB administra su contraseña inicial efímera. PostgreSQL UID999 y solo el inicializador de volumen usa root+CHOWN sin red. Trust en socket local se limita al contenedor DB; TCP usa SCRAM. Modelo de amenaza: host y daemon confiables.

El perfil es un runner de experimento cerrado P4.3, sin comandos/rutas de cliente y con timeouts. No amplía network=none globalmente ni el executor Python/corporate. Interrupción gestionada conserva recibo de fallo y limpieza; esa rama no se certifica con una prueba de señales en P4.3. SIGKILL/fallo del daemon sigue requiriendo inspección manual; nunca se atribuye recuperación automática.

## Limitaciones y decisiones antes de P4.4

- El preparador Prisma advierte que no detecta libssl/openssl en el Node slim y selecciona fallback openssl-1.1.x. Generate/migrate/typecheck/build/PrismaPg y los casos aquí descritos **sí funcionan**. No se oculta el aviso ni se generaliza compatibilidad a otros comandos/plataformas. Revisar una imagen con OpenSSL explícito antes de ampliar el stack; cualquier cambio requerirá nueva matriz/digest/validación. No se instaló software en el host para silenciarlo.
- Next añade allowJs/incremental/isolatedModules en el tsconfig de la copia de validación y actualiza next-env.d.ts durante build. El core original queda intacto. Normalizar esos defaults antes de congelar un futuro producto en P4.6; no es aún evidencia de reproducibilidad de generación business.
- Compose es una base local con proyecto preparado montado readonly, no una imagen app de distribución. Empaquetado/generación/autonomía siguen pendientes; no hay production-ready.
- El modelo técnico pertenece a fixture de validación. Antes del producto real habrá que seleccionar explícitamente schema/historial auth/módulo sin trasladar TechnicalSmoke automáticamente. No se crea auth anticipadamente.
- Linux/amd64 y daemon local confiable; sin prueba de otras plataformas, SIGKILL, fallo físico, backup, rotación de credenciales o recuperación automatizada. Nunca usar prune global.
- Revisión de vulnerabilidades/operación de imágenes pendiente; Better Auth exacto, esquema auth, sesiones, cierre de registro y bootstrap de primer usuario de aplicación deben diseñarse/validarse solo en P4.4 autorizada.

Se solicita revisión de esta entrega y sus límites antes de cualquier P4.4. P5–P7, publicación, secretos/datos reales e infraestructura externa permanecen fuera de alcance.
